# Blast radius（影响面）

在变更交付前，找出它会在别处破坏什么。用于「blast radius of X」「what could this break」，或评审一个你还不敢信的小 diff。

`how` 和 `why` 的同伴。`how` 告诉你代码做什么。`why` 告诉你它为什么长成这样。影响面告诉你它会在别处破坏什么。

罗列调用方不是这份工作。智能体一秒就能 grep 出来。这份工作是 grep 找不出来的破坏。

## 别信你自己的分析文字

听起来有道理的影响面分析一文不值。无论真假，它读起来都令人信服。所以不要只交回分析文字。找出整个判断依赖的一两个事实，用运行代码来证明它们。

### 你有多确定

对变更安全性依赖的每个事实，在成本允许的范围内沿这份清单往下走，并说明停在哪一级。

1. 你说的。单凭这个一文不值。
2. 你指到了那一行。真实的 `file:line`，或库自己的源码。
3. 你证明了坏情况不会发生。你逐步走了一遍失败路径，它到不了。
4. 你跑了。一个调用真实代码的脚本或测试，你错了它会大声失败。
5. 你在运行中的应用里复现了它。

第 4 级通常是一个小脚本：引入应用交付时用的同一个库，调用你担心的那个确切函数。

## 步骤

1. 读变更。diff、它新增／修改／删除的符号、它现在的行为有何不同，包括 diff 没写明的部分。拉取 PR 及其提交。
2. 找出它安全所依赖的那一个事实。多数看似危险的变更之所以安全，靠的是单个事实，比如「这个调用只丢弃已经死掉的缓存条目，别的什么都不做」。找到那个事实。它成立，大多数危险情形就一次性排除了。把时间花在这里，不是一长串「可能」上。
3. 看 grep 止步的地方。读你调用的库的源码，核对它锁定的版本和任何本地补丁。弄清事情何时运行：微任务、卸载与清理、Solid 与 React 的差别。追符号搜索漏掉的东西：API 返回的 JSON、数据库列、传输格式、读同一份字节的另一种语言、功能开关、下游三跳之外的代码。
4. 对每个风险诚实。给它真实的发生概率和真实的代价。保留你确认的风险。查过并排除的单独列出。引用真实的 `file:line`；一无所获的搜索也是答案；绝不编造调用方或 API。
5. 证明那一个事实。写一个运行真实代码的脚本或测试，运行它，粘贴发生了什么。
6. 变更大或波及广时，按 `arena` 运行。把同一个问题问多个模型，合并答案。不同模型抓到不同的真实 bug。

## 交回什么

- **它做什么。** 改了什么，包括不显眼的部分。
- **它安全所依赖的那一个事实。** 陈述它，说明你把它证到了第几级，展示证明。证不了就写「未证明」。
- **风险。** 每条写明怎么坏、`file:line`、概率和严重程度、怎么检查。重要的那些贴出证明。
- **已排除。** 你查了什么，为什么没问题。
- **合并之前。** 能抓住真实 bug 的最便宜的测试或复现，包括你写的脚本。

通过 `unslop` 来写，引用真实代码，去任何公开地方之前剥掉私密内容。

**回复：** 上面的分析，那一个安全事实要么已证明，要么标注未证明。
