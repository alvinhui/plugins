# Automate me（自动化沉淀我的风格）

引导式流程，把用户的工作惯例变成智能体会遵循的技能。产出是为其量身定制的一个 `-mode` 技能（如 `jay-mode`、`priya-mode`）。

本技能编排另外三个：内联的挖掘环节（见第 1 步）、Cursor 内置的 `create-skill`（编写）、**unslop** 技能（文字纪律）。它编排顺序，不替代它们。

## 流程

### 0. 检查已有技能

递归查找与用户 handle 匹配的 `.cursor/skills/**/*-mode/SKILL.md` 和 `~/.cursor/skills/*-mode/SKILL.md`。mode 技能可以放在个人分类目录（`.cursor/skills/<handle>/`）里，不一定在顶层。已存在时，用 `AskQuestion` 确认意图（除非用户已说过「update my skill」之类的话）：

- 更新已有技能（重复运行时的默认选项）
- 从头开始（少见，做之前先问为什么）

更新模式会改变后续流程：
- 第 1 步只挖掘技能上次编辑之后的历史（`git log -1 --format=%cI <path>`）。
- 第 2 步问什么变了、缺什么，而不是从零开始要沉淀什么。
- 第 4 步就地编辑已有文件。用户没有推翻的章节保留。有新证据的章节修订。只为真正的新规则新增章节。

### 1. 挖掘用户历史

并行分发前先定位当前工作区的会话记录。系统提示里写明了工作区的 `agent-transcripts/` 目录。只用那个路径。不要跨 `~/.cursor/projects/*/` 做 glob，那会越过工作区边界，读到无关项目的私密会话。

在该范围内排查近期智能体对话中反复出现的模式。跨历史切片跑多个并行子智能体（如最近 2-4 周，切成 3 片让每片有足够素材）。按 **poteto-mode** 技能 Subagents 一节的要求，为每个子智能体按任务选择推理级别。每个切片挖掘子智能体从父智能体提供的工作区限定路径读会话记录，找下面的信号，返回一份简短的结构化模式清单，附证据指针。默认值得找的信号：

- 回复偏好（长度、语气、格式、「说人话」类纠正）
- 委派习惯（子智能体、模型、专门工作流、并行）
- 验证姿态（「完成」的定义、单元测试还是实测复现、评审者）
- 代码与文字纪律（风格、引用的原则、lint/格式化工具）
- 流程惯例（worktree、提交、PR、评审/合并工具）
- 元偏好（任务中途修技能、提议新技能）

提升一个信号前先跨切片交叉核对。2 个以上切片都出现的模式置信度高。孤立信号弱，通常丢弃。

### 2. 直接问用户

挖掘会漏掉尚未出现过的意图。用 `AskQuestion` 工具（结构化多选），别让用户从零打字。

形状：一两个问题，每题 4-6 个选项，类别类问题设 `allow_multiple: true`。先问宽的（「哪些方面最重要？」），再对选中的方面追问具体选项。结构化轮次之后，用一个自由问答兜住选项漏掉的内容。

不要一口气抛 20 个问题。

### 3. 聚类发现

把汇总的信号归入章节。常见的有（只用适用的）：

- **回复风格**：长度、语气、格式。
- **自主性**：不问就做多少、MCP 工具的使用。
- **先理解**：界定或调查改动时该用哪些技能。
- **子智能体**：默认策略、并行、模型配任务、专门工作流。
- **文字／代码纪律**：原则、lint 工具、风格指南。
- **评审与验证**：复现姿态、验证技能、实测工具。
- **流程**：git worktree、提交、PR、评审/合并工具。
- **技能**：编写技能的习惯、先修技能、提议新技能。

**poteto-mode** 技能展示了形状。读它把握粒度，不要抄它的内容。用户的规则和 poteto-mode 的不一样。

### 4. 起草技能

用 Cursor 内置的 `create-skill` 技能编写。放置规则：

- 路径：保留已有 mode 技能的分类。新 mode 时，若仓库已为该 handle 建有个人分类，用 `.cursor/skills/<handle>/<handle>-mode/SKILL.md`。否则默认放项目里的 `.cursor/skills/<handle>-mode/SKILL.md`（用户偏好个人技能时放 `~/.cursor/skills/<handle>-mode/`）。
- Handle：用户的名或选定的标识。
- frontmatter `description`：按用户的名字＋`/<handle>-mode`＋「按用户的风格工作」触发，不用「write code」「review PR」这类泛化关键词。
- frontmatter 格式：遵循 `create-skill` 的 YAML 规则。`description` 保持单个 YAML 标量。标点或换行需要时加引号，或用 `description: >-` 加缩进续行。
- frontmatter 默认 `disable-model-invocation: true`。只有用户明确希望其 mode 每一轮都生效时才关掉。

### 5. 打磨文字

对每一行应用 **unslop** 技能和 `create-skill` 的写作指南。

把草稿给用户看，收反馈。预期多轮迭代。狠心删。mode 技能不是使用手册。

### 6. 落地

在基于 main 的 worktree 里工作。提交并开 PR。不要直接推 main。

## 护栏

- **不要过拟合单次对话。** 说过一次、另一次又被推翻的偏好是噪声。写成规则前要求多个实例。
- **不要耍聪明。** 复述其他技能的内容、发明比喻、给智能体读者写「诗意」文字，都是只有成本没有收益。保持可操作。
- **引用，不内联。** 用户依赖的其他技能以路径引用出现，不贴摘录。用户在别处维护的原则文档同理。
- **章节保持最少。** 只有用户在某处有具体的、非默认的规则才加章节。「沟通清晰」不是一个章节。「短段落。比较选项用表格。条目真正并列时才用列表。」才是。
- **称呼用泛称。** 祈使句里用「用户」或「人类」，不用作者的名字。
- **不强行对称。** 用户没有值得写下的流程规则时，整个流程章节跳过。

## 评估

`-mode` 技能是主观产物。`create-skill` 式的测试/迭代基准循环在这里没用。和用户做感觉核对：读起来像用户本人吗？漏了什么吗？然后交付。

只有技能的触发准确率在实践中真成了问题，才跑 description 优化循环。

## 何时不用

- 用户要的是任务专用技能（不是工作惯例）：只用 `create-skill`，无需挖掘。
- 用户想沉淀一个狭窄工作流（如「我怎么写提交信息」）。那是普通技能，不是 mode 技能。
