# Technical writing

写到让一个疲惫的工程师第一遍就读懂。

- 删掉每一个不干活的词。
- 用短的日常词："use"，不用 "utilize"。
- 一条规则让句子变得更糟时，换个方式改句子，或者不动它。
- 写真实的符号、文件、flag 或命令名，不写同义词或对它的描述。
- 不造行话。用开发者会说出口的词。有名字的模式第一次出现时说明它的含义。

## 变化节奏

- 长短句混用。承载两个想法的句子拆开。只承载一个想法的长句保留。
- 解释类文字要有观点。参考类文字保持干巴巴。
- 要具体。不写「schema 变更可能引发问题」，写「重命名一列会让构建失败」。

## 先选模式（Diátaxis）

一份文档一种模式。不要混模式。拆开再互相链接。

- **Tutorial（教程）：边做边学。** 说清学习者将做出什么。每一步产生可见的结果，并说出他们应当看到什么。解释只给一个从句加一个链接。
- **How-to（操作指南）：达成目标的步骤。** 解决读者的问题。假定读者有能力。只写动作。允许分岔。按任务给指南命名。
- **Reference（参考）：供查阅的事实。** 只做描述。干巴、完整、确定。结构镜像被描述对象的结构。
- **Explanation（解释）：理解与缘由。** 一个有边界的主题。给出上下文：设计决策、历史、约束、备选方案。观点只允许出现在这里，别处不行。

## 把句子写给读者（Google 开发者风格）

- 用「你」称呼读者，用现在时。
- 说清谁做什么。只有动作主体未知或无关紧要时才用被动。
- 指令写成命令。条件放在指令之前，常见情况放在前面。
- 不用buzzword，不用比喻，不说「请」，步骤里绝不出现「只需」「轻松」「快速」。
- 不预告下文，相邻句子不用同一个短语开头。
- 链接文字要说出链接去向。
- 标题承载要点，用句子式大小写。每页一个 h1，不跳级。
- 顺序用编号列表，其余用无序列表。列表前用一个完整句子引入。各项保持并列结构。
- 代码用代码字体。UI 元素加粗。用连续逗号（serial comma）。删掉「等等」。

## 让陈述一次只上一个载荷（STE 规则）

- 一句话一条指令。其他地方一句话一个想法。
- 超过约 20 词的指令、超过约 25 词的其他句子，拆开。
- 警告或条件放在它守护的步骤之前。
- 保留 "the" 和 "a" 这类冠词。
- 每个词一个含义，每个动作固定用一个词。
- 步骤写成直接命令，绝不写成叙述，绝不用被动。
- 能避开 "-ing" 词就避开。

## 不让任何句子有两种读法（Global English）

- 「只」「不」这类词紧贴它们修饰的词。
- 拆开长名词串。
- 每个「它」「他们」「这」都指向一个明确的对象。绝不用「这」或「哪个」指代整个从句。
- 不省略动词，也不省略 "that" 这类标明结构的小词。
- 并列结构中重复冠词能防误读时就重复。说清 "and" 或 "or" 连接的是哪些部分。
- 用句号，不用分号或长破折号。不用斜杠，不用 "(s)" 表复数。括号里的文字要是完整的语法单位。
- 每个东西在所有地方都叫同一个名字。
- 不用习语、口语、拉丁缩写和比喻。

## 语气与本仓库的具体要求

- 本技能触及的每份文档都应用 **unslop** 技能。AI 腔模式目录归它管：AI 词汇、填充词、模糊限定、格式痕迹。
- PR 描述和提交信息也是写作。除 Diátaxis 外的每一层都适用于它们。PR 正文是一份审阅者一分钟内能读完的简报。不要粘贴 swarm 日志、SHA 清单或指标表格。给链接。
- 产品 UI 文案不是文档。它们遵循你产品的文案规范。
- 代码片段用 tab 缩进。写真实路径。每个数量或目录树的论断，在落地它的那个提交上必须为真，并附上能重新生成它的命令。
