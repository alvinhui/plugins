# TDD Bug 修复

修一个有清晰、便宜测试路径的 Bug 时，先把坏掉的行为变成可执行的测试，再改生产代码。目标是一个聚焦的回归测试：修复前失败，修复后通过。

测试不切实际时不要硬造。如果可用的测试需要大面积的执行框架搭建、脆弱的 mock、缓慢的端到端基础设施、只有生产环境才有的状态、模糊的复现步骤，或大量无关的夹具改动，就不加新测试，改用最接近的有用验证。

## 工作流

1. **理解 Bug。** 确定预期行为、当前行为、受影响的路径，以及最小的可观察复现。
2. **选最窄的可执行检查。** 优先用该代码路径已有的最近的单元、组件、集成或回归测试。没有明显可行的测试路径时，不要为了满足流程而从零造一个。
3. **先写失败的测试。** 加上本能捕获这个 Bug 的最小聚焦测试。测试应编码预期行为，而不是照抄当前实现。
4. **修复前先跑新测试。** 确认它因预期的原因失败。它通过了、或因无关原因失败，先修测试或复现，再改实现。
5. **修 Bug。** 做满足预期行为的最小生产改动，同时保住相邻契约。
6. **重跑回归测试。** 确认测试现在通过。

## 失败测试不切实际时

改用最接近的可执行回归检查：针对性脚本、手动复现命令、浏览器自动化、快照对比、日志断言，或聚焦的集成检查。

宁可不加新测试，也不加坏测试。坏测试是这些：主要在测 mock、编码当前实现细节、依赖时序或无关全局状态、为一个小修复需要昂贵基础设施、或证明修复后马上就会被删掉。

## 护栏

- 不要为了迁就错误实现而改测试。
- 不削弱既有断言，除非预期行为确实变了且原因清楚。
- 回归测试聚焦这个 Bug。避免大面积夹具改动或无关的覆盖扩张。
- Bug 是偶发的，就尽量让测试确定化，并记录被锁定的信号。
- Bug 暴露出更大一类失败时，先落地聚焦的回归路径，再考虑追加同类覆盖。

## 最终回复

报告证据，不只报结果：

- 点名修复前失败的测试或可执行检查，以及它产生的失败。
- 点名修复后通过的测试运行，以及做过的相邻验证。
- 拿不出修复前失败的证据时，说明原因，并描述改用的最接近的回归检查。
