# Maintain a verification skill（维护验证技能）

应用一变，功能地图就开始腐化。本技能是 `/create-verification-skill` 生成的技能（或任何带功能地图的项目本地验证技能）的保养循环。严谨的单位是功能，不是每个句子：从源码覆盖每个功能文件，并实时操作每个功能，但不必对每个条目都穷究到底。

## 结果

选一个，并说明是哪个：

- **clean** —— 每个功能都得到源码和实时覆盖；没有值得交付的东西。不建分支，不开 PR。
- **changed** —— 一个 PR 交付已证明的文档、执行框架或地图修正。
- **blocked** —— 覆盖无法完成，或已证明的修复无法安全交付。准确说明是什么挡住了。

## 编辑范围

只编辑验证技能自己的目录（它的 SKILL.md、features/，以及它拥有的执行框架脚本）。运行期间绝不编辑产品代码：地图描述的行为应用已不再具备时，要么是文档漂移（修地图），要么是产品回归（报告它，不要在文档里掩盖）。

## 巡检

0. **定位目标。** 找到要维护的验证技能：正文含启动/驱动章节和功能地图的项目本地技能（通常是 `.cursor/skills/verify-*/`）。多个候选 → 问是哪一个；一个都没有 → 停下并指向 `/create-verification-skill`，不要凭空发明目标。

1. **索引卫生。** 读功能地图 README，glob 它的同级文件。修掉缺失、多余、重复或失效的条目。轻量处理；不生成清单。

2. **源码波次。** 每个功能文件一个只读子智能体，并发启动。每个从源码解释「这个面向用户的功能如何工作？」，带引用地标记可能的文档漂移，并返回一条简明的实时验证配方。子智能体绝不驱动应用，绝不编辑文件。返回形态：功能摘要／源码入口／可能的漂移或无／一条配方。

3. **对账。** 每个功能文件都有返回的摘要。把重叠的配方合并成尽可能少的应用状态。抽查被引用的漂移；不要重新证明干净的断言。扫一遍近期变动，找地图缺失的面向用户的界面——断定缺失之前必须有具体的源码路径。

4. **实时巡检。** 即使源码看起来干净也必须做。协调者负责全部驱动；遵循验证技能自己的启动模型——服务器和 UI 用一个长生命周期实例串行驱动，短生命周期 CLI 每次驱动一个全新隔离会话（由该技能的 Launch 一节决定，不是本节）。每个功能至少操作一次，并且无论出现什么失败，全程守住三条不变量：（1）实例上次做出意外行为之后没做过体检，就绝不驱动它——首次驱动前体检，以会话为单位时每个新会话都体检，任何失败的驱动之后再体检；体检看不到故障时（健康进程上卡死的 UI 状态），重置到已知状态或重新启动，而不是心存侥幸；（2）已采集的证据在每次清理后都存活，到指明位置核实，不靠假设；（3）驱动启动的任何东西都不比该驱动的有用期活得更久——失败迭代的残留一律清理，无论会话是卡住、退出还是共享（共享实例清残留，不清实例）。技能漂移导致的体检失败就是漂移：在编辑范围内修复并重试一次——只重启被修复弄失效的东西，不多重启——之后才把巡检判为 `blocked`。无法到达的功能只有在给出具体前置条件（鉴权、权限、操作系统、外部状态）和尝试过的路线后才能标 `verified-unreachable`；地图漏写该前置条件就是漂移。分诊得出的任何执行框架修复，交付前都要重新实时驱动。最终拆卸发生在本次运行最后一次驱动之后——包括那些重新证明——让任何东西都不比运行活得更久（证据按技能规定保留）。

5. **分诊。** 用户视角描述错误或缺失 → 文档漂移，修掉。行为正常但执行框架驱动不了 → 执行框架缺口，修掉；执行框架修复遵循与生成时相同的辅助脚本规则（脚本可执行，调用方式写进技能正文）。应用行为真的坏了 → 产品缺口；为用户记录下来，不进这个 PR。

6. **交付或停止。** changed：一个 PR 承载已证明的修正，先重读每个改动的文件。clean 或 blocked：不开 PR，如实报告结果和覆盖情况。

把简明的运行笔记（覆盖的功能、不可达的前置条件、确认的漂移、结果）放在临时位置；不要提交它们。
