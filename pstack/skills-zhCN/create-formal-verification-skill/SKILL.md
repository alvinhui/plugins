# Create a formal verification skill（创建形式化验证技能）

测试检查的是有人想到要写的那些情形。形式化验证检查声明范围内的每一种情形：模型中步骤的每一种顺序、某个界内的每一个输入，或全部输入。本技能找到仓库中最需要这种保障的部分，验证它的一条性质，并留下一个项目本地技能，让下一个智能体能对照该性质检查改动。这个技能要写给一个在改动中途冷启动阅读、从未见过你的工作的智能体。用户必须能不学验证语言就信任结果并据此行动。

## 从代码中选目标

从代码库回答，只把观察不到的部分拿去问用户。用户点名了某个区域或 bug 时，从那里开始。

好的目标是代码做出的一个承诺：违背它会伤害用户，而测试很少触及违背它的情形。选仓库中这类目标里最强的一个，不是最容易验证的那个。

## 让问题选择工具

选能以最低成本回答问题的工具：模型检查器、证明助手、基于 SMT 的验证器，或其他工具。「事件会不会以糟糕的顺序发生」通常适合对设计的小模型跑模型检查器，任何语言下默认用 TLA+。「代码本身对每个输入是否行为正确」，如内存安全、溢出或数据结构不变量，通常适合直接跑在代码上的验证器。没有验证器支持这门语言时，明说，并用生成的输入测试真实代码，而不是给函数手工建模。必须在任意规模下成立、有界检查不够的性质，可能需要证明。优先选仓库开发者能安装并运行的工具，并告诉用户你为什么选它。

## 什么才算好

- **忠于代码。** 模型或证明的每一部分都指向评审者能打开的代码。验证视为一个不可分割步骤的，在代码里也是一个不可分割步骤。名字来自本仓库。
- **能够失败。** 从未见过失败的检查什么也证明不了。让每条性质在其守护代码的破坏变体上失败一次，比如删掉一个检查或调换一个步骤的顺序。
- **发现就是发现。** 当前代码违背性质时，用代码自己的术语连同反例一起报告。不要为了通过而削弱性质或模型，除非用户要求，否则不改产品代码。
- **对范围诚实。** 说明验证了什么、在哪些界和假设之下、遗漏了什么。通过覆盖的是模型或那个界，不是整个系统。
- **不用工具也能读懂。** 性质和危害各用一句平实的话说清。反例用代码自己的词汇讲成一小段步骤序列。
- **重跑成本低。** 一条命令、可复现的工具版本、足够短的运行时间，让下一个智能体在每次相关改动时都会用它。
- **与代码保持同步。** 记录每个检查覆盖哪些文件和函数，以及你最后一次实验证验证仍描述它们时的提交。被覆盖的代码在该提交之后变化时，下一个智能体能看出验证需要再看一遍。

## 生成 verify 技能

写一个项目本地技能，frontmatter 点名区域并说明何时使用。没有 frontmatter，技能永远不会注册。仅凭这个技能，下一个智能体必须能判断改动是否触及被验证的代码、运行检查、区分真 bug 和建模错误，并在改动是有意为之时更新验证。把覆盖记录和同步提交放进技能，并告诉下一个智能体：只有确认验证描述了新提交上的代码之后，才能把同步提交前移。使用本仓库真实的命令、路径和名词，不留占位符。

如果检查是 TLA+ 模型，告诉下一个智能体用 pstack 的 [`/statechart`](../statechart/SKILL.md) 技能解读每个结果。它把检查器发现的每个不变量违背以最短路径用平实语言展示。检查通过时，`/statechart` 画出系统如何在状态间迁移的图。按名字引用 `/statechart`。它的命令、选项和文件路径随版本和机器变化，所以一个都不要复制进生成的技能或其脚本。

## 交付前先证明

像下一个智能体那样，把生成的技能完整走一遍，对象是一个在真实代码中破坏该性质的临时改动。它必须抓住这个破坏。然后丢弃临时改动，确认检查回到起点：通过，或只在你将报告的发现上失败。从未运行过的 verify 技能是草稿。技能漏掉破坏或某一步跑不起来时，修技能或验证，而不是修临时改动。

## 交付

告诉用户：你验证了什么、用了哪个工具及原因、界是什么、检查用平实语言发现了什么、如何运行、不覆盖什么。只有发现了接近的候选时才建议第二个目标。引导用户使用 `/maintain-formal-verification-skill`，在没有复查的改动之后把验证拉回与代码一致。
