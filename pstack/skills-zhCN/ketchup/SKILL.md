# Ketchup（进展同步）

向用户同步本会话自其在 `/ketchup` 之前写的最后一条消息以来的变化，帮 TA 理解每个变化，而不只是进展到哪。然后摆出每个等 TA 拍板的决策，让 TA 只凭你的回复就能拍板。通知和子智能体结果不算用户的消息。假定用户只记得自己的最后一条消息，之后的都不记得。

用 [`/bro`](../bro/SKILL.md) 的口吻，不做它的任务：平实的词、短句、无行话，像一个人给另一个人讲进展。说用户身上变了什么，不说你怎么做的。说「测试通过了」，不说「CI 绿了」。哈希、文件路径、命令、构建号、测试计数一律省略，除非用户需要它才能行动。每个 PR、分支或智能体都用用户认识的名字称呼，不用你发明的标签。一个事实需要上下文才讲得通时，要么给上下文，要么不提这个事实。

## 收集变化

本轮保持只读。只用已有的东西做图：不改代码、不启动应用或任务、不发布任何内容。收集那条消息之后你自己的工作、子智能体的报告，以及本会话里其他人的消息。核对本会话碰过的每个 PR、CI 运行或智能体的当前状态。要展示的每个数字都对照它的来源事实核对，纠正过的要说明。

行动项是只有用户能做的决策或步骤，比如产品选择、审批、不可逆操作，或你没有的权限。仍在等用户的都要列入，包括其最后一条消息之前提出的。你自己还能做的工作不是行动项。绝不编造决策来凑回复。用户没要求、工作也不需要的步骤不是行动项，除非它不可逆且在等用户：给一行文字，不配图。

一个决策可以覆盖多个事项，比如一组待合并 PR 中的每一个。为每个事项收集：链接、它给用户带来什么变化、你的推荐背后的证据、风险、你的推荐。决策需要而你不知道的事实写「未知」。没有的链接就不给。

## 写回复

字数花在决策上，不花在过程叙述上。「发生了什么」控制在 100 词以内（图不计入），发生得少就更短。对用户毫无变化的工作不提。每个事项约 30 词。回复随事项数增长：两个事项总共应远低于 150 词（图不计入），三十个就需要多得多。绝不为了压字数砍事项或缩水：不能用数量代替清单，不能用链接代替事项。链接可以补充深度，但只凭回复必须足够拍板。

开头一句短话，点名什么在等用户，或说明没有。细节由行动项给出。什么都没发生、也没有等用户的事，就照实说然后停。

然后展示发生了什么，图在前。内嵌工作产出的截图和视频，再放解释变化的示意图。然后对用户要求的每件事各给一条短要点：结果如何，是完成、仍在运行、失败还是未检查。每行按你会说出口的方式写：「搜索慢是因为缺索引」，不是「搜索复查：完成」或「慢搜索：缺索引」。途中发现并修掉的 bug 要点名。每行单独读也要成立。仍在等用户的事绝不标成完成，行动项里会说的内容这里省略。摘要之下，最多给三行能改变用户认知或行动的短话。再用一行点名你自己还能做的剩余工作。

然后列出行动项。提出归用户的决策，比如合并、批准或选择，并给出你的推荐。你会先做的步骤写进推荐。必须先发生的事、无法撤销的事也写进去。决策涉及的每个 PR、issue 或智能体给出编号或链接，选项间抉择时同样如此。

形状随决策而定。只涉及一个事项的决策就一条要点：决策、你的推荐、给用户带来什么变化、推荐背后的证据、风险，事项只点名一次。多个事项共享一个决策时，决策和推荐只写一次，然后每个事项各一条要点，风险最高的在前：链接和名称、给用户带来什么变化、推荐背后的证据、风险。事项的推荐只在与整体推荐不同时才写。每个事项的风险都要给，哪怕很低，比如「低风险：只改颜色。」等待的代价只在超出拖延时才说，比如截止日期或数据丢失。

选项间抉择时，列出工作权衡过的每个选项，各写它给用户带来什么、代价是什么，有当前状态的写状态。这些代价就是该决策的风险，不再单列风险行。上方截图展示了选项时，把每个选项的收益和代价写在它的截图下面。

## 视觉

视觉指图片：截图、视频、Mermaid 图、`/visualize` 出的图表或示意图、生成的图像。Markdown 表格不是视觉，哪怕带前后对比列。

一件事画成图比写成句子更好懂时，就画：设计或系统如何工作、带各 PR 状态的 PR stack 或依赖链、修复前后对比、选项并排。绝不画状态清单、行动项清单，或没有连线的方框。同一个事实绝不给两遍，无论文字里还是图之间。

每张图小到一眼能读完：至多六个方框，每框至多八个词。标签写人会说的平实话，不写「Tests: pass」这种标签式短语。需要一句话才讲得清的事实放正文，或者不放。

变化可见时把截图和视频内嵌，不只给链接。可见变化没有图时，其摘要行标注「暂无截图」，并在那里说明屏幕上变了什么。示意图和图表只用你掌握的事实画：连接关系用 Mermaid 图，数字用 `/visualize` 图表。绝不编造数字，绝不画出或生成你没截过的屏幕。只链接存在的产物。
