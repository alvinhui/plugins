### 爬坡优化

**你负责指标和实验的严谨性。监督并评审，委派尝试。** 适用于围绕一个可测量的东西、朝一个目标做持续的迭代改进。一次性修复走 Bug fix 或 Perf issue。这里是循环。

核心纪律：一次改动、一次测量、保留或回退。绝不叠加未测的改动，也绝不凭读代码宣布胜利（**prove-it-works** 原则技能）。

1. 选指标之前，先摸清工作负载和架构。追踪目标，点名能左右结果的真实工作负载维度（数据规模、历史、状态、并发），选一个能复现用户抱怨的用例。没有用例能复现，就先修复复现，而不是爬坡优化。然后钉死一个指标、算作更好的方向，以及一个可检查的停止判据：目标配上尝试次数下限，让早期撞上的好运无法结束运行（示例「比基线至少好 50% 且至少迭代 10 次」就是这个形状）。用户给了数字就用用户的，否则商定一个。
2. 搭建测量执行框架，证明它的灵敏度，然后冻结（**build-the-lever** 原则技能）。跑有对比度的真实工作负载，确认目标用例复现症状、更轻松的用例按预期拉开差距。执行框架分不开它们，就修改工作负载或指标。冻结前用 **benchmark-checklist** 技能审查执行框架，并让它打印错误计数和完成工作量计数。冻结后，一条可重复的命令产出指标，采样次数足以越过噪声（N 次的中位数，不是单次运行）。任何改动之前，记录基线指标和回归关口（必须持续通过的测试）的一次通过运行。
3. 通过 **show-me-your-work** 技能开决策日志。一个 `decision.tsv`，每次尝试一行：id、假设、改动、前值、后值、差值、测试、结论（保留或回退）、备注。每次尝试前先读它。放在 git 树之外（gitignore）。
4. 每个假设都落在第 1 步的架构模型上，点名具体机制（「把 X 挪出启动路径，因为它阻塞首次绘制」），而不是「试试给什么加 memo」。性能指标按 Perf issue playbook（`playbooks/perf-issue.md`）第 2 步的性能口诀给假设排序。只借它们的顺序，不借那一步的停止规则。
5. 循环，每次迭代一个假设：
   - 把改动交给子智能体，使用你配置的 hillclimb 模型（默认 `claude-opus-5-5-xhigh-fast`），范围收紧。按 Subagents 一节的要求，为每个子智能体按任务选择推理级别。监督并评审 diff，而不是自己敲（**guard-the-context-window** 原则技能）。多个独立假设同时在跑时，并行分发给子智能体，各在自己的 worktree 里（**separate-before-serializing-shared-state** 原则技能）。
   - 用冻结的执行框架测前值和后值，并跑回归关口。
   - 只有指标越过噪声移动且关口保持通过才接受。否则完整回退改动。「可能有帮助」的小调整不保留。
   - 每个接受的修复一个提交，只暂存你改过的文件（`git add <files>`，绝不 `-A`）。无论保留还是回退，都记下那一行。
   每次迭代以一次检查收尾，再开始下一次（**sequence-verifiable-units** 原则技能）。无人值守运行时，只从 Autonomous run playbook（`playbooks/autonomous-run.md`）借唤醒机制，不借它的停止规则。
6. 突破第一个平台期。停滞、连续几次被拒时，换类别、组合差一点的方案、重读源码，或试更激进的东西，然后才下「山已爬完」的结论。正确性和简洁性高于数字。破坏行为的胜利要回退，守住数字的简化要保留（**laziness-protocol** 原则技能）。
7. 判据达成，或剩余想法收益边际、不值其成本时停下。不要为了达标放宽判据，也不要在还有廉价未试假设时放弃。卡住就上报，不要空转。
8. 执行 **Opening a PR**，把接受的提交按落地顺序叠好。

**回复：** 指标和目标、基线到终值及百分比差值、迭代次数（保留与回退各多少）、每个接受的修复一行、`decision.tsv` 路径，以及若继续推进你会试的下一个最佳想法。
