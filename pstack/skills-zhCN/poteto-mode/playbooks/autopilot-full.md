### Autopilot-full

**你负责结论，从不负责 PR。每个 PR 由一个负责人从构建带到合并；在你的 swarm（它从不写这些代码）证明将要落地的代码之前，什么都不合并。**

结论覆盖一个补丁，CI 通过覆盖一个当前提交。第 4 步只完整跑一次 swarm，只有重大改动才再跑一次。`playbooks/shipping.md` 的 patch-id 规则可以延续一条验证通道的结果，但每个新提交都需要自己的 CI 通过。

1. **操作者的检验关口优先。** 授权只覆盖队列里的条目，所以操作者点名归自己的条目和队列之外的 PR 停在可合并状态。要求陈述计划不等于放行。
2. **每个 PR 派一个负责人，并把它的工作放在接替者能找到的地方。** 整个程序只解析一次代码托管平台。默认用 GitHub CLI（`gh`）。如果 `command -v origin` 成功且 Origin 能解析该仓库，所有 PR 操作都用 `origin pr`。否则留在 `gh` 并记录这次回退。绝不依赖 Graphite（`gt`）。每个负责人都是 Cursor 云端智能体：构建、按 `playbooks/opening-a-pr.md` 开 PR、在真实产物上证明改动、按 `playbooks/babysit.md` 看护到检查通过，并在第 4、5 步放行后合并。该 playbook 要求报告 rebase 的地方，由负责人 rebase 自己的分支并用 `git push --force-with-lease` 发布。

   尽早开 PR，让 CI 和机器人与工作并行跑。只有做完去冗（`cursor-team-kit` 插件的 `deslop` 技能（`/deslop`））和 `/no-comments` 清理，代码才算就绪，让完整 swarm 跑在成品代码上。然后 rebase 到当前 trunk，在自证之前报告代码就绪的当前提交，让验证跑在补丁将要落地的 base 上。之后每个新提交都要报告，自证、CI 和看护完成后报告可合并。修复轮次留在那个 base 上，除非 trunk 冲突、弄坏 CI，或落地了已知的对相同文件的并行改动，因为每次 rebase 都会重启 CI。在推送代码就绪版本之前，以及之后需要验证者的推送之前，在已提交的当前提交上跑仓库中覆盖所改路径的检查。

   假定 VM 会死掉。启动后尽快推送，并按 **show-me-your-work** 技能在根智能体的存储（路径见系统提示）里开一条决策记录，之后每完成一个单元就先推送再开始下一个。派出子智能体的人把它的 id、状态，以及依同类历史运行得出的卡死时限记进该存储，让父智能体死掉后根智能体还能探测它。只 force-push 自己的分支，`--force-with-lease` 钉在你最后推送或接管的 SHA 上；发现任何不是你做的推送，停下并报告根智能体。
3. **各负责人基于 trunk 并行运行，绝不叠 stack，** 让每个 PR 各自落地。
4. **swarm 只完整验证一次。** 完整 swarm 在代码就绪的当前提交上跑一次。只有新增行为、重新设计或大量新 diff 才再跑一次完整 swarm。rebase、解决合并冲突或小修复，在新提交上只派一个验证者；纯措辞改动不派。按 **swarm** 技能在代码就绪的 SHA 上并行分发独立验证者。它们重跑检验关口，通过对应控制技能（如 `cursor-team-kit` 的 `control-ui` 或 `control-cli`）或指定的驱动器在真实界面上实测承重行为，并审计 diff。缺了实测通道，或你还没审计可合并报告的凭据，结论就不算干净，因为任何通道都不信任自己没查过的断言。

   只为你能展示的问题拦下 PR：当前提交上的失败运行，或被该 PR 弄错的文档行。PR 的 base（无论 trunk 还是 stack 中它下面的 PR）已有的问题不构成拦截，除非该 PR 复制了它或新触达了它。只有用户会踩到的 bug、失败的检验关口、交付出去的错误文档才拦截，其余都进后续事项。
5. **负责人只合并你验证过、且在将要落地的 trunk 上测过的内容。** 仅有 CI 通过绝不授权合并。swarm 的各条通道启动后，合并准备把分支 rebase 到当前 trunk，报告新提交，等待 CI 通过。

   临合并前 fetch trunk，问一句它的改动会不会影响补丁，因为逢 trunk 移动就 rebase 永无止境。当将要落地的代码从未被测过——比如冲突、双方都改过的文件、或该 PR 要跑哪些检查发生了变化——就 rebase 并等 CI。双方都改过的 lockfile 无需 rebase，只要在合并结果上 frozen install 通过、且该 PR 改动的包在那里的解析结果与当前提交一致，因为这次安装测的就是将要落地的 lockfile；安装失败则说明 rebase 必须修好它。当 trunk 改了补丁的调用方或补丁依赖的东西（比如它调用的代码或依赖版本），在合并结果上跑补丁的检查，通过就合并。否则直接合并。如果 trunk 会迫使合并准备之后再来第三次 rebase，暂停并报告根智能体，由它编排相撞的工作。
6. **运行根层。** 任何放松检验关口的动作，比如调高预算或加白名单条目，都需要验证者的证明加上你新鲜的会签，因为想要通过的是负责人。在覆盖审批的授权下，这次会签就是审批，负责人对它的记录指向你的会签，供通道核查。被禁用或软失败的检查一律要暴露出来，因为它不再守护每一种情况。绝不给出或绕过代码托管平台强制的审批，因为任何会签都覆盖不了它。

   经操作者放行后，布防 `/loop 1h` 持续审计，直到没有委派出去的工作，因为长时间运行会漂移、智能体会无声停滞。每次 tick 从 trunk 重读本 playbook 并修正漂移，比如未报告的提交或未记录的智能体，让其负责人补记，因为漂移是记录里的缺口，不是停滞。它探测每个智能体，直到叶子通道，按副作用逐个判断，因为状态文本和摘要可能掩盖卡住的子智能体。智能体报错、无法开启回合、或超过卡死时限仍无新产出，就是卡住了；到第一次 tick 既没推送也没写记录行的负责人同样算卡住。在等你或操作者答复的不算卡住，去答复它。卡住的智能体立刻替换，不等它停下来。某次 tick 若改动了与操作者相关的东西，结束时按 **ketchup** 技能向其同步进展；什么都没改就保持安静。
7. **操作者叫停就立刻收队。** 暂停以零写入命令传达到每个负责人。各自报告进展并保留任务简报，直到操作者解除。

**回复：** 按 **ketchup** 技能向操作者同步进展，覆盖每个 PR 的状态和结论、合并了什么、会签及其理由、待操作者的检验关口、搁置的后续事项，并附各 PR 和记录的链接。
