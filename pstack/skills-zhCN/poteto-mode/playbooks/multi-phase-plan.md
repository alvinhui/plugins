### 多阶段或多 PR 计划

**你负责计划，不负责代码。计划是一份清单，负责人逐格执行，操作者凭证据审计。** 计划就是交付物。不要实现。

1. 改动只涉及一两个文件且做法显而易见时，跳过计划。说明后停下。
2. 动笔前按 `playbooks/prototype.md` 用原型解决悬而未决的问题。只有任何运行都无法裁决的产品或偏好决策才问操作者。
3. 写计划文件。开头写改什么、按落地顺序排列的 PR id，以及依赖图：哪些 PR 独立、从 trunk 拉分支，哪些等哪些，各自可以碰哪些文件。然后每个 PR 一节。一个 PR 就是一个改动，带自己的证据（**sequence-verifiable-units** 原则技能）。每节用复选框列出：它依赖什么、编辑哪些文件、构建的那一个改动、能看到的结果、它的验证。
4. 只有测试不算充分验证。unit、live、perf 三类复选框全部勾上，PR 才算通过验证。每个 live 复选框用具体场景和通过判据驱动真实界面。perf 复选框点名指标、探针、先测的 trunk 基线，以及判失败的数字。改变交互的 PR 要等操作者评审后才合并。
5. 交回计划路径并停下。执行从操作者明确放行开始。

**回复：** 计划路径、各 PR id 及其依赖和需评审放行的集合、仍未证明的内容。
