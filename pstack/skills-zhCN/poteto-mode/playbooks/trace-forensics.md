### Trace 取证

**你负责从产物中得出诊断。**

区别于给运行中进程插桩的 **Runtime forensics**（运行时取证）。这里采集已经完成。产物是固定的数据集，读它，不要重新运行。工具保持通用：cpuprofile 和 `.json.gz` 用 DevTools 或 trace 解析器，spindump 用文本编辑器，heapsnapshot 用你的堆分析工具。

1. 识别格式，用正确的工具加载。大产物交给子智能体解析（**principle-guard-the-context-window** 技能），把归约后的发现留在主线程。按 Subagents 一节的要求，为每个子智能体按任务选择推理级别。
2. 把原始产物转换成可查询的形式。把 trace 或堆快照导入 sqlite，每个采样、栈帧或节点一行。先达到可查询的形态再开始读。
3. 收窄到原因。查询占用时间最多的栈帧，沿调用树走到热路径。泄漏则沿保留链从泄漏对象追到 GC root。spindump 则找出卡在 CPU 上或被阻塞的线程及其等待原因。
4. 归因到源码。用产物自带的符号把热栈帧映射到文件、符号和行号。没有源码映射的栈帧还不算诊断。解析符号，或者明确说产物里没有符号。
5. 如果有配对的采集，对比前后两份产物来确认。否则把发现标记为产物所支持的最强假设，而不是已确认的原因。
6. 交回有出处的诊断，未被要求就不做修复。原因查明后路由到 Bug fix 或 Perf issue。吞吐量检查点保持一行：`throughput checkpoint: n/a, read-only forensics`。

**回复：** 产物及其格式、归约后的发现、源码位置、产物路径，以及配对采集是否确认了它。
