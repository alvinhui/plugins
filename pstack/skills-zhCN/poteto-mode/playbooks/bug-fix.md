### Bug 修复

**你负责这个任务。规划、评审、验证。** 把调查和修复委派给子智能体，自己保持主导。按 Subagents 一节的要求，为每个子智能体按任务选择推理级别。

讲科学。交付的每一行都能追溯到运行时证据。「可能有帮助」的冗余保险是假设，不是修复，不交付。证据推翻假设时，回退它引出的改动。只交付证据支持的最小改动，不多一行。

1. 通过控制技能（见 Non-negotiables 一节）在对应界面上亲自复现，即使某个调试或插桩协议说要请用户复现。只有给出明确、具体的理由说明控制界面无法触达目标，且已把控制界面驱动到极限之后，才请用户出手。无法直接复现时，合成触发条件、收紧条件，或插桩直到它触发。
2. 二分查找原因。列出候选假设，逐个排除直到只剩一个。用受影响子系统的 trace 和查回归历史的 **why** 技能给假设打底。每一轮选能砍掉最多剩余问题空间的切分，拿运行时证据，排除。程序状态不明时，加插桩或日志，在代码运行时读取。不要猜。用 Cursor 的 `/loop` 命令驱动漫长或顽固的追查。在进入第 3 步的 `architect` 或 `interrogate` 并行分发之前，用运行时证据确认幸存的*机制*。
3. 规划修复。跨越函数边界就先 `architect`。把实现委派给子智能体，使用你配置的 bug-fix 模型（默认 `claude-opus-5-5-xhigh-fast`），并给出明确范围。
4. 在同一界面上验证。原始复现现在通过。「INCONCLUSIVE」或错误的验证界面不算通过。明确标记出来。单元测试展示的是分支行为，不是 bug 不存在。
5. 编排提交，让失败的复现在 git 历史里先于修复落地。bug 有廉价的本地测试路径时，参照 **tdd** 技能的失败测试先行节奏。测试昂贵、重集成或不明确时跳过。
   这就是 **sequence-verifiable-units** 原则技能的标准形态：失败测试在前，修复叠在上面。
6. 执行 **Opening a PR**。

**回复：** 哪里坏了、根因、修复、你如何验证。逐字粘贴先失败后通过的复现输出。
