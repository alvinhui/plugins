# Figure it out（自己想办法）

任务匹配不到任何 playbook 时，就设计一个。写任何代码之前的交付物是工作流本身：一个阶段序列，按任务缩放严谨度，运行科学方法，并留下人类离开后回来也能审计的决策记录。

## 开始

建一个待办列表，第一项是读 **poteto-mode** 技能的 Principles 一节。然后把下面的阶段加为待办。

## 阶段 A：框定

先摸清情况，再定案。在你能说清以下几点之前，不要开跑：

- 完成的定义，写成可证伪的判据（**prove-it-works** 原则技能）。
- 量化的范围：粗略的单元数和工作量，加上摸底发现的阻塞项。
- 严谨度档位，宁高勿低。单向门决策和高影响面的工作多给。可逆、低风险的步骤少给。严谨度是检验关口和产物，不是「更努力」。

投入长时间运行之前，先展示框定和取舍。可逆工作直接推进（**never-block-on-the-human** 原则技能），但数小时的运行值得设一个检查点。

## 阶段 B：设计工作流

分解成原子的、可独立合并的单元。风险最大的未知排最前。脚手架和验证先于功能（**foundational-thinking** 原则技能）。

- 开工前先建验证执行框架，基线取自变更前的状态，让检查读起来是「旧值对新值」。
- 单向门的设计决策，运行 **architect** 技能（它会运行 **arena**）。形状已经具体的机械性工作跳过它。对已定案的设计再跑一次 arena 是过度工程（**laziness-protocol** 原则技能）。
- 决定哪些并行分发。只沿着接缝并行，给每个工作智能体自己的 worktree 或分支（**separate-before-serializing-shared-state** 原则技能）。不要过度分发。按 **poteto-mode** 技能的 Subagents 一节，按工作为每个子智能体选推理档位。
- 把设计好的阶段列表写下来。人类评审的就是这份列表。

然后执行这个设计。把它的步骤作为具体条目加进待办列表，放在阶段 C 和阶段 D 条目之间。每一步都在阶段 C 的循环纪律下运行，并把阶段 D 的日志穿插其中：每步落地记一行，而不是把整份记录留到最后。

## 阶段 C：运行循环

每个单元是一次实验。陈述假设，做最小变更，在真实产物上对照判据测量，有推进就保留，没推进就回退。应用 **sequence-verifiable-units** 原则技能，验证完每个单元再开始下一个，而不是把检查攒到最后。

- 通过检查产物来验证，绝不靠自述。东西通过得太容易时，先怀疑观察方法，再怀疑系统。
- 委派的工作要配一个评审。工作智能体钻检验关口的空子，就重置并加固契约。检验关口本身错了，就用单独的变更修检验关口，而不是绕开它。
- 结论只有 VERIFIED、NOT VERIFIED、INCONCLUSIVE 三种。INCONCLUSIVE 不是通过。不要隐瞒负面结果。

## 阶段 D：保留审计记录

通过 **show-me-your-work** 技能记录这次运行。figure-it-out 的工作通常足够大，值得把记录提交，让评审者在 PR 里读到。记录加 diff，才能让人类回来时信任这份工作。

## 阶段 E：验证并交回

在真实产品上、而不只是执行框架上，对照阶段 A 的判据检查整体。把任何反复出现的纠正编码为检验关口、lint 规则、检查或脚本（**encode-lessons-in-structure** 原则技能）。

**回复：** 你设计的 playbook、严谨度档位及原因、决策记录的路径、哪些已对照判据验证、哪些仍未解决。
