# 措辞提示词（Word the prompt）

提示词陈述意图和完成检查。步骤由 playbook 提供，所以几句平实的话胜过一份规格书。

## 要写的

- 目标。说清哪里不对，或用户想要什么。
- 完成检查。能判通过或失败。「变好一点」和一个时长都不是检查。
- 要展示的证据。要真实的命令输出、流程视频、存储值，或前后对比数字。
- 用户已知的信息。一个症状、一步复现、一份日志或一个链接，都能省智能体一次搜索。
- 真实约束。「先复现」「先别改任何代码」「零行为变化」「继续前先让我评审」，每一条都会改变智能体的做法。

## 不要写的

- 怎么做。说要达成什么，给智能体留找更好办法的空间。
- 技能或步骤清单。手写的顺序会丢掉或打乱 playbook 保留的步骤。只为推翻某一个选择才点名技能。
- 用户对原因的猜想，等智能体重述问题之后再说。先给出的猜测会收窄搜索。

## 先装载上下文

- 报告杂乱时，让智能体在做任何事之前，用自己的话、平实地重述底层问题。误读会在任何代码出现之前暴露。
- 新会话里，先 `/recall` 该主题的早前工作。旧会话存着新智能体缺的上下文。
- 改不熟悉的代码前，用 `/how` 问机制、`/why` 问缘由。没有追踪过模型的智能体会在第一个看似合理的位置修症状。
- 让 `/teach` 为一个选择立论，如「说服我它修的是原因而不是症状」。论证比摘要好核查。

## 先设计再计划

- 绝不接受第一版设计。要几个方案的原型，UI 配截图或视频，凭证据选。
- 让原型回答悬而未决的问题。不要对抗式评审抽象计划，评审者会发明根本不会发生的风险。
- 共享包或 API，先要 README 或教程，再倒推回代码。文档成为智能体自查的靶子。
- 设计定了才要计划。计划的每一步以一次检查收尾。

## 追问要短

- 会话已装着任务时，"do it"（做吧）、"continue"（继续）、"keep going until done"（一直做到完成）就是完整提示词。
- 换话题时以 "new task"（新任务）开头。否则模式会把消息当成下一步。

## 离开之前

- 说 "im going to bed"（我要睡了）或 "im stepping away"（我要离开了），让智能体不再发问。
- 把完成写成每次迭代都能跑的检查，把该判据交给 `/loop`。
- 要一个基于指定 base 的新 worktree。
- 预先回答智能体会停下来问的事，如 "don't ask me before committing"（提交前不用问我）。
- 要一份供事后审计的决策日志。
- 给出口：「几个小时后真卡住了，就停下并写清原因」。

## 一行转向

- 重述目标："i said the goal is to repro. i did not ask for a fix yet."（我说过目标是复现，还没让你修。）
- 点名原则：「应用 prove it works。给我真实输出，不是构建日志。」
- 原则名管用，因为智能体已经读过那条规则。它的回复会点名该规则改变的决策。
