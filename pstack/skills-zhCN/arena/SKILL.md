# Arena（竞技场）

启动任何东西之前，先建一个待办列表，每个阶段一条（框定、并行分发、交叉评审、选基底、嫁接、验证）。

## 阶段 A：框定

每个候选拿到相同的提示词，所以提示词就是契约。

1. 写明每个候选要产出的产物。
2. 推导评分标准：3-6 条具体、可打分的评价准则，描述成功在*这个*任务上是什么样子。它是阶段 D 里挑选者的工具。候选只看到任务本身。
3. 从 `~/.cursor/rules/pstack-models.mdc` 的 `arena runners` 行选跑者，默认是 `claude-fable-5-2-high`、`claude-opus-5-5-high-fast` 和 `gemini-4-neon-xhigh`。`auto` 或 `inherit-parent` 条目就是父模型，此时省略 `model` 并以 `generalPurpose` 派生。如果 Task 工具拒绝某个 slug，改用同家族最接近的有效 slug，或去掉这个席位，至少保留两个跑者，并说明情况。家族按前缀判断，最长匹配优先：去掉开头的 `cursor-` 之后，依次是 `claude-fable-*`、`claude-*`、`gemini-*`。其他 slug 的家族是第一个连字符之前的文本。有多个设计方向就多派生几个；工作受生成量限制而非判断力影响时，可以重复用同一个模型。按 **poteto-mode** 技能的 Subagents 一节为每个子智能体选推理档位。
4. 按 **separate-before-serializing-shared-state** 原则技能，给每个候选自己的输出位置（尽量用 git worktree，否则用 `/tmp/arena-<slug>/candidate-<n>/`）。

## 阶段 B：并行分发

在一条消息里派生全部 N 个子智能体，设 `run_in_background: true`，每个都带上任务、共享背景材料的路径、自己的输出路径，以及指令：产出产物和一段简短的理由说明，写明它考虑过哪些备选、否决了什么。

如果某个候选没有产出，就以 N-1 继续，并记录这次掉队。

## 阶段 C：交叉评审

阶段 B 的候选全部完成后，从 `~/.cursor/rules/pstack-models.mdc` 的 `arena cross-judge pool` 行派生一个只读评审，默认是 `claude-opus-5-5-high-fast`、`gemini-4-neon-xhigh`。评审绝不能来自父模型的厂商，且 Fable 在这项检查中算作 Claude，所以选另一家厂商的第一个条目。`auto` 或 `inherit-parent` 条目就是父模型。如果你不知道父模型是什么，就用第一个真实 slug，并说明厂商检查没有执行。如果 Task 工具拒绝某个 slug，改用同家族最接近的有效 slug，再不行就用下一个此类条目，或跳过评审，并说明情况。你在阶段 D 阅读时，评审按路径标签给每个候选逐条评分标准打分，并推荐一个基底。

## 阶段 D：选基底

挑选之前把每个候选从头到尾读完。对照评分标准逐条打分，不凭整体感觉；阶段 C 跑了交叉评审就与它比对。双方对基底意见一致，就确认了这个选择。不一致说明你们之一有偏见，或评分标准含糊。决定之前把两份理由说明都读了。

选未来维护者最容易在不破坏不变量的前提下扩展的基底。两个感觉打平时，按 Laziness Protocol 选边界更干净或 API 更小的那个。

## 阶段 E：嫁接

把每个落选候选再过一遍，找值得移植进基底的东西，通常每个候选一两处，而不是大部分。按 **redesign-from-first-principles** 原则技能，手工把每处嫁接融入基底，让结果在同一个心智模型下保持连贯。不要机械粘贴。

如果候选收敛到同一个形状，这是强一致。记录下来，直接交付共识形状，不需要嫁接。如果它们严重分歧，说明阶段 A 定义不足。重新框定并重跑，而不是把分歧折中平均。

## 阶段 F：验证

按 **prove-it-works** 原则技能，像验证任何其他输出一样验证合成产物。如果验证发现 arena 漏掉的问题，要么阶段 A 错了（重新框定并重跑），要么某个候选抓住了它而你漏了嫁接（回到阶段 E）。不要粉饰。

## 输出

一个合成产物，旁边附一段简短的合成说明，写明：基底是哪个、为什么；交叉评审的结论，或阶段 C 跳过了评审；每处嫁接及其来源候选；否决了什么、为什么；有无收敛或掉队；以及验证结果。
