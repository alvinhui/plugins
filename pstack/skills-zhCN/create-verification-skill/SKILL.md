# Create a verification skill（创建验证技能）

每个严肃的项目都需要一套脚本化的方式来驱动真实应用并证明行为：启动它，像用户那样操作一个功能，采集证据。本技能把这套方式生成为一个贴合仓库的项目本地技能（`.cursor/skills/verify-<app>/`）。生成器的产出是写给下一个智能体的，不是写给人的：它会被一个从未见过这个应用的智能体在任务中途冷启动阅读。

## 1. 审问仓库，而不是审问用户

从代码库回答以下问题，只把观察不到的部分拿去问用户：

- **界面：** 用户实际接触的是什么？Web UI、CLI/TUI、桌面应用、API、移动应用，还是库？一个仓库可能有多个；选主要的那个，其余记下来。
- **运行：** 应用如何在本地启动？优先用仓库自己记录的开发命令（package scripts、Makefile、README 快速上手）。记下端口、环境变量、种子数据、鉴权。
- **驱动：** 智能体如何以编程方式与它交互？先找现成的执行框架——Playwright/Cypress 用例、expect 脚本、PTY 辅助工具、可 curl 的端点、调试端口。之后才选通用配方：Web 和 Electron 用浏览器/CDP，CLI/TUI 用 tmux/PTY 执行框架，服务用普通 HTTP。
- **观察：** 能采集哪些证据？截图、终端记录、响应体、日志、退出码、数据库状态。
- **隔离：** 两个实例能否并排运行（端口、数据目录、profile）？不能的话，在生成的技能里写明：拒绝双重驱动共享实例，好过破坏用户的会话。

如果检出的代码不能原样构建或启动，先修好（或精确报告）再生成；对着坏基线写出的技能会教出错误的步骤。当无关的缺失资源挡住启动时（API 从不提供的静态目录、示例配置），生成的技能可以创建它，明确标记为验证脚手架，并在清理时移除。

## 2. 生成技能

写 `.cursor/skills/verify-<app>/SKILL.md`，带 YAML frontmatter（`name: verify-<app>`，`description` 写明应用、界面和何时使用——没有 frontmatter 技能永远不会注册），以及以下各节，每节都基于审问实际发现的内容（不留占位符）：

- **Launch（启动）：** 为验证启动应用的确切命令，以及如何判断就绪（一行日志、一个提示符）。启动必须能从空数据目录达到可用状态，包括所有迁移和种子数据。就绪意味着可用，不只是进程有响应。数据库健康检查可能在初始化脚本还在跑时就通过。包含拆卸步骤。短生命周期的 CLI 或 TUI 没有需要保活的服务器：启动意味着构建二进制（或安装依赖）一次，然后每次驱动都在自己隔离的 PTY 或 tmux 会话里开始。
- **Doctor（体检）：** 一个只读检查，回答「这个实例值得驱动吗？」——进程在跑、版本/构建正确、端口归我们所有、鉴权有效。任何看起来不对劲的时候，智能体先跑它。
- **Drive（驱动）：** 执行框架配方，用本仓库真实的选择器/命令，不是示例。优先用稳定的句柄（ARIA 标签、data 属性、提示符字符串、路由路径），而不是坐标和 Tab 顺序。
- **Evidence（证据）：** 为证明采集什么、放在哪里。写明证明标准：走真实的用户路径，而不是内部 setter 或仅供测试的端点；采集动作和随之产生的状态，不只是最终画面；在可见内容之外验证副作用（写入的文件、插入的行、发出的消息）；只在生产边界已经隔离外部系统的地方使用 mock。当安全路径是 dry-run 或测试模式时，通过观察（文件、网络、git 引用）验证它实际跳过了什么，而不是相信它的名字：有些 dry-run 仍会访问网络或打开浏览器。
- **Cleanup（清理）：** 如何拆掉本次运行创建的实例。绝不按进程名杀进程；只杀你启动的。清理移除实例和临时状态，绝不移除证据：证明产物在技能指明的位置存留，不被拆卸销毁。
- **Helpers（辅助脚本）：** 技能附带的任何脚本都可执行，且其调用方式写在技能正文里。需要读者反向工程才能用的辅助脚本不算辅助脚本。

## 3. 播种功能地图

创建 `.cursor/skills/verify-<app>/features/README.md`，并为你能识别的每个面向用户的功能各建一个文件（起步先做最重要的 3-5 个，来自路由、命令、菜单或文档）。遵循 [`references/feature-map-example/`](references/feature-map-example/) 的形态：一个 README 索引，每个功能一个文件。每个文件从用户视角回答：功能是什么、如何到达、如何用执行框架驱动、什么可观察的终态能证明它工作。四个 H2 是 `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>` 和 `Gotchas`。如果种子数据缺少某条用户旅程需要的前置条件，该旅程报告失败，原因写进那个功能的 `Gotchas`。绝不为了让旅程通过而削弱它。这份地图是仓库持续维护的验证依据；地图列出了多个入口时，只驱动一个顺手入口的证明是不完整的。

## 4. 交付前先证明生成的技能

把它自己的指令完整跑一遍：启动、体检、驱动地图中的一个功能（一个就够；地图的存在就是让后续运行覆盖其余）、采集证据、清理。清理之后，确认证据仍在指明的位置——把证明吃掉的清理算这一步失败。修掉失败的地方，并且每次失败的迭代之后也要跑生成的清理，让失败的尝试不遗留进程和端口。从未执行过的生成技能是草稿，不是交付物。如果你是在真实目标的替身上证明的（用容器代替全新 VM、用本地栈代替远端），列出替身做过而目标不会做的每一个准备步骤。这些步骤在真实目标上的运行覆盖它们之前，始终未验证。

## 5. 提供维护循环

引导用户使用 `/maintain-verification-skill`，在应用变化时保持地图诚实。只在用户询问时才建议执行频率。
