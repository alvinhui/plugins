# Recall（召回工作上下文）

**在开始或恢复工作之前，你要重建用户近期的工作上下文，交回一份紧凑的摘要：现在进展到哪、下一步做什么。**

保持紧凑、切题。只读范围内线程需要的内容，然后停。

你的上下文存在于两份记录里。你自己的聊天历史记录你做了什么、决定了什么。共享记录记录同一份代码周围以别的名义发生的一切：用户反复报告的症状、交付后又被回退的修复、生产环境仍在触发的错误。第二份记录存在于源码管理、问题跟踪器、聊天和问题频道、长文档和错误跟踪里。一个拖着长 bug 尾巴的功能，大部分故事都在那里，所以不要只凭你的对话记录重建它。

对话记录在 `~/.cursor/projects/<slug>/agent-transcripts/<uuid>/<uuid>.jsonl`，其中 `<slug>` 是工作区路径去掉开头的斜杠、每个「/」换成「-」（所以 `/Users/you/proj` 变成 `Users-you-proj`）。每一行是一条聊天消息。

1. 先分类，再路由。要恢复某个具体的既往聊天，用 `session-pickup` playbook，不是本技能。把习惯沉淀成持久技能是 `automate-me`。给人读的工作总结是另一类任务。recall 是在你行动之前，跨近期聊天加载工作上下文。如果用户已经给了完整的状态摘要（路径、分支、变更），直接用它，跳过挖掘。
2. 搜索之前锁定范围。钉死时间窗（「近期」是一个真实区间，默认最近 7 天）、指名的主题，以及工作区（默认当前活动的。没被要求就绝不读别的项目的对话记录）。把范围复述回去。绝不悄悄把「全部」变成「最近 N 个」。
3. 在你的聊天历史上并行分发。用快而便宜的模型派生并行子智能体，每个负责语料的一个切片。告诉每个子智能体：按真实修改时间排序候选（`ls -t`），绝不按 UUID 名字排；先 grep 主题，再只读匹配的聊天、且只读相关区域；跳过当前聊天和明显的噪声（子智能体、评测和测试聊天）。每个都返回同一套 schema，每个聊天一块：主题、用户目标、决策、未结线程、遇到的困难和纠正、产物（PR、工单、分支），每条都引用聊天 UUID。只有一两个聊天时，跳过并行分发直接搜。原始对话记录留在子智能体里，主线程只拿它们的发现。按 **poteto-mode** 技能的 Subagents 一节，按工作为每个子智能体选推理档位。
4. 只要主题指名了功能、文件、子系统、领域或 bug，就清扫共享记录。这是默认动作，不是酌情判断，「我在 X 上的工作」也不例外。每个来源派生一个调查子智能体，用 agent 模式，因为 readonly 会剥掉 MCP 访问权限，问每个：「当前状态是什么，试过什么没站住，用户还在报告什么」。与聊天历史挖掘并行运行。空结果也是发现。不可用的 MCP 跳过并说明。把返回的内容并进简报。只有不指名目标的纯活动召回（「我这周做了什么」）才跳过这步，那时你自己的历史和实时状态就是全部答案。
5. 对照实时状态验证。拿挖掘和清扫发现的 PR、分支、工单，用 `git` 和 `gh` 核对。当答案取决于某个智能体实际做了什么（它运行的工具、读的文件、撞到的错误）时，读完整对话记录，而不是裁剪过的本地副本。
6. 按下面的契约写简报。按线程分组。紧扣指名的主题。

## 输出契约

先摘要，再线程状态，再问题，最后下一步。更深的细节放后面，或者砍掉。

- **摘要。** 至多 5 条。这份工作是什么，整体进展到哪。
- **线程。** 每条一行，前面恰好一个状态标签：`[merged #N]`、`[open PR #N]`、`[in flight <branch>]`、`[verified, uncommitted]`、`[reverted #N]` 或 `[planned, not started]`。没有标签的线程就是还没完成，给它打标签。
- **问题。** 至多 5 个，反复出现的那些。包含用户反复报告的症状，以及任何交付后被回退的修复，让下一次尝试从上一次失败的地方开始。
- **下一步。** 唯一最有用的下一个动作，要具体。

相邻的功能或工单不写入，除非它阻塞当前工作。摘要加线程行超过一屏时，先砍细节，再砍线程。通过 **unslop** 技能写简报，聊天发现引用 UUID，共享记录发现引用来源（PR 号、工单 ID、聊天固定链接、错误跟踪 issue），任何公开输出之前先清理私密上下文。

**回复：** 简报，符合上面的契约。
