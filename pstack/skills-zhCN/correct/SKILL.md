# Correct

操作者在这个仓库里反复纠正智能体的同一批错误。改造仓库，让下一个智能体犯不了这些错。

假定每个贡献者都是一个智能体：它只看得见自己打开的文件，照抄最近的示例，走能编译的最短路径。把仓库设计成：从单个文件看起来对的改动，对整个仓库也对。

## 找出错误类别

先读最近的提交、revert、评审意见、智能体指令文件，以及解释变通方案的注释。把错误归成类别。一个类别发生过两次才算数。

## 在能起效的最高层级修掉每个类别

1. **用架构消灭它。** 每份状态一个所有者，每件事一种受支持的做法。隐藏内部实现，让错误的 import 直接失败。用单一事实来源取代手工同步的清单。删掉智能体会照抄的旧做法和死代码。
2. **用类型强制它，让坏状态写不出来。** 如果坏代码仍能编译，加一条 lint 或 CI 检查，报错信息里写明该改用哪个文件、类型或函数。如果这种模式已经很普遍，只在改动新增它时才失败。
3. **测试行为。** 修掉或删掉这样的测试：它检查的行为坏掉时它仍通过，或只有内部实现变化时它却失败。
4. **文档或智能体规则最后写，只写给需要判断的地方。** 智能体跳过它们时不会有任何东西失败。

## 修复并证明

然后现在就修最高频的类别，每个类别一个提交。证明每个新检查都能在一个真实的历史错误上失败。本地和 CI 跑同一条命令。豁免写在出问题的那一行上，附理由、到期日和一个人的批准。

## 维护规则表

最后，在智能体指令文件里维护一张表，把每条规则和强制它的机制配对。操作者纠正你时，修掉错误并加上规则。如果规则本来就在、却没有任何机制强制它，那就是重犯，在同一次改动里用最高层级修掉它。一旦某个错误不可能再发生，就删掉对应规则。

**回复：** 每个类别及其证据、你选的层级、以及更高层级为什么行不通。
